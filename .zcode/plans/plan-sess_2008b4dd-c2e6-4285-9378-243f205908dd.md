## 透明代理（Linux / macOS）设计与实现

### 调查得到的三个前提事实

1. **Linux/macOS 装不上内核（阻塞项）**。`pickMihomoAsset` 只接受 `.zip`（`updater.go:614`），但我查了官方 release v1.19.29 的 127 个资产：Linux/macOS 全是 `.gz`，只有 Windows 是 `.zip`。所以当前在 Linux 上连 mihomo 都下载不到，透明代理无从谈起。**必须先修这个。**
2. **进程无提权路径**。`exec.Command` 不带 `SysProcAttr`（`manager.go:163`），无 root 检测、无 capability 检查、无 `exec.LookPath` 探测。Docker 镜像跑 `USER aurora:aurora`(uid 10001)，`cap_add: NET_ADMIN` 只进 bounding set，非 root 拿不到 effective 位——`docker-compose.yml` 的注释已记录这个陷阱。
3. **配置层无"强制字段"钩子**。三层模型 base→remote→override，override 只处理 proxy/rule。注入 tun/tproxy-port 的唯一自然插入点是 `config_service.go:700` `GenerateYAML` 之前。

### 阶段一：修阻塞项 + 后端能力（无 API 变更）

**1. 支持 .gz 资产**（`updater/updater.go`）
- `pickMihomoAsset` 按平台选扩展名：Windows `.zip`，其余 `.gz`
- 新增 gzip 解压分支（单文件流，非归档），与现有 `unzip` 并列
- 保留 `compatible` 优先、`Size` 校验、落盘后 `-v` 自检
- 排除 `.deb/.rpm/.pkg.tar.zst`

**2. 新增 `backend/internal/netcheck/` 环境检测包**（纯只读探测）

按 build tag 拆平台：`detect_linux.go` / `detect_darwin.go` / `detect_other.go`（沿用 `signal_unix.go`/`signal_windows.go` 范式）。

检测项：
- **权限**：`os.Geteuid()==0`；解析 `/proc/self/status` 的 `CapEff`/`CapBnd`/`CapAmb`，测 bit 12(NET_ADMIN)/13(NET_RAW)/10(NET_BIND_SERVICE)
- **TUN**：`/dev/net/tun` 与 `/dev/tun` 是否存在且为字符设备；`/proc/modules` 或 `/sys/class/misc/tun`
- **TProxy**：`exec.LookPath` 探 `nft`/`iptables`/`ip6tables`/`ip`；`iptables --version` 判 legacy vs nf_tables；`/proc/modules` 查 `nft_tproxy|nft_socket|xt_TPROXY|xt_socket`；内核版本 ≥4.19
- **busybox ip 识别**：`ip --version` 不含 `iproute2` 则标记不可用（busybox 的 `ip` 不支持 `ip rule add fwmark`）
- **容器**：`/.dockerenv`、`/proc/1/cgroup`；比对 `/proc/self/ns/net` 与 `/proc/1/ns/net` 判 host network
- **发行版**：`/etc/os-release` 的 `ID`/`ID_LIKE`；包管理器 `apk`/`apt-get`
- **sysctl**：读 `ip_forward`、`rp_filter`、`route_localnet`
- **macOS**：仅 TUN，需 root（无 capability 机制），device 必须 `utun<N>`

产出结构化结果：每种模式 `available/blocked/reason`，缺依赖时附**具体安装命令**（`apk add --no-cache iptables ip6tables nftables iproute2` / `apt-get install -y --no-install-recommends iptables nftables iproute2`）。按你的选择**只检测不代装**。

**3. 防火墙管理 `backend/internal/netcheck/firewall_linux.go`**（TProxy 用）
- 专用容器：nft `table inet aurora_tproxy`；iptables 回退用自建链 `AURORA_TP_*`
- 拆除只删自己那张表/链，**绝不** `iptables -F` / `nft flush ruleset`
- 应用前快照 `iptables-save`/`ip6tables-save`/`nft list ruleset`/`ip rule show`/`ip route show table all` 到 `<ConfigDir>/netbackup/`
- 规则要点：管理端口(22/面板/9090)优先 RETURN → LAN CIDR RETURN(除 UDP/53) → `-m mark --mark 0xff -j RETURN`(排除内核自身出站，不加会自环并触发已知高 CPU) → DIVERT 链(已建立 TCP) → TPROXY
- 策略路由 `ip rule add fwmark 1 table 100` + `ip route add local 0.0.0.0/0 dev lo table 100`
- nft 先 `nft --check` 干跑校验

**4. 配置注入**（`config_service.go:700` 前）
- 开关开启时按模式覆写 `result.Config`：TUN 写 `tun.enable/stack(mixed)/auto-route/auto-redirect/auto-detect-interface/dns-hijack`；TProxy 写 `tproxy-port` + `routing-mark: 0xff`
- 关闭时确保 `tun.enable: false`
- 复用既有 `TUNConfig`（`domain/config.go:144`，`AutoRoute *bool` 指针语义已就绪）
- 冲突校验：`auto-detect-interface` 与 `interface-name` 互斥；`route-address-set` 与 `routing-mark` 互斥

**5. 开关与回滚状态**（KV settings 表，无需迁移）
- `transparent.enabled`、`transparent.mode`、`transparent.pending_confirm`、`transparent.applied_at`
- **不具备条件时强制关闭且不可改**：service 层校验，检测不通过直接拒绝写入
- **强制确认 + 持久化回滚**：开启后写 `pending_confirm` 到数据库并起 90 秒倒计时；用户须在界面点"确认网络正常"，否则自动拆规则并关开关。持久化是关键——面板自身崩溃/重启后仍能从数据库恢复并回滚

**6. 测试**：netcheck 各探测项（用假 `/proc` 数据与临时文件）、配置注入结果、规则生成文本快照、回滚幂等性

### 需要你知道的取舍

- 你未回答的两个风险问题，我按工程默认取了更安全的选项（专用表/链+快照、强制确认+持久化回滚）。如与你的想法不同，实现前告诉我。
- macOS 只有 TUN 一条路（`redir-port` 在 macOS 需自己写 pfctl `rdr` 规则，且 pf 无 UDP 重定向、无 TPROXY 等价物），且必须 root。
- TProxy 让面板改宿主防火墙与路由，是本方案最高风险处。我会把管理端口豁免、快照、回滚做全，但**首次启用建议你在有物理/控制台访问的机器上验证**。
- Docker 默认镜像跑非 root，要用透明代理必须调整 compose（root + 去掉 no-new-privileges + 映射 tun 设备），这会降低容器隔离性，文档里会明确写出代价。
